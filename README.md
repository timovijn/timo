# timo

A native, local-first iPhone and iPad daily planner built with SwiftUI. Requires iOS 26 or later and a compatible Xcode installation. There are no third-party dependencies, accounts or network requests.

## Run on your iPhone

1. Open **Timo.xcodeproj** in Xcode (not Package.swift).
2. Select the **Timo** project in the left sidebar, then the **Timo** application target.
3. Under **Signing & Capabilities**, leave **Automatically manage signing** enabled and select your **Personal Team**. If the bundle identifier is unavailable, change `com.timovijn.timo` to a unique identifier.
4. Connect your unlocked iPhone, trust the Mac and enable Developer Mode if prompted.
5. Select your iPhone as the destination beside the Timo scheme and press **⌘R**.

A free Personal Team can install the app on your phone. You must run it again from Xcode when its seven-day provisioning profile expires. Keep the same bundle identifier and update the installed app rather than deleting it to preserve its local data.

## Run in Simulator

Open the same project, select an installed iPhone Simulator as the destination and press **⌘R**. No signing team is needed for Simulator. If a runtime is missing, install it through Xcode Settings → Components.

## iPad

The app runs natively on iPad in every orientation, so it also works in Split View and resizable windows. The layout is the iPhone's: the day list, time view and persona pages keep their rows to a reading width of 680 pt, centred, while swipes still work across the whole screen; the dock's buttons stay in the corners and the calendar keeps its 380 pt width. The editor and other sheets open as centred form sheets. On iPhone the screen is narrower than that width, so nothing changes there except in landscape on the largest phones.

## Try the first version

- An empty day shows only a quiet “Nothing planned” line; the add button in the dock starts it.
- Tap **+** to create an item with a title and day. The title wraps visually but never contains line breaks: Return (labelled Done) closes the keyboard, and pasted line breaks become spaces. Tapping anywhere outside a text field, or opening a schedule or reminder popover, also closes the keyboard; the tap still reaches whatever it landed on. The Schedule section is one line of inline capsule buttons: the day, **Add time**, and, once a time is set, **+ End**. The day reads Today, Tomorrow, Yesterday or a weekday within the coming week, otherwise a short date; its popover offers Today / Tomorrow / Next week above a calendar and closes on a choice. Schedule popovers always open below their button (arrow on top) at a fixed width, so the calendar is never squeezed beside the leftmost button. **Add time** picks a start after the day’s last timed item and not before now (rounded up to a quarter hour; the next whole hour today when nothing else is planned; otherwise 9:00) and opens a popover with that suggestion, 9:00, 12:00 and 18:00 above a time wheel. **+ End** opens duration choices (15m, 30m, 45m, 1h, 2h) on one evenly divided line (wrapping only at large text sizes; VoiceOver reads full durations) above an exact end date and time. A duration sets the end time and leaves the popover open so the end can be checked or fine-tuned. The button shows the end time itself: “until 10:30”, or “until Saturday, 10:30” on a later day; and the end can only be after the start. Set times carry an ✘ inside the capsule (with a 44-point tap target); removing the start also removes the end, but the duration is remembered while the editor is open and comes back when a time is added again. Buttons animate in and out (immediately under Reduce Motion), adding or removing a value gives a selection haptic, and the capsules wrap at large text sizes. VoiceOver reads them as Day, Time and End time with full values (for example “Ends 29 Oct 2026 at 11:00, 1 hour”), Add time / Add end time, and Remove time / Remove end time. There is no Task/Event selector.
- Schedule and reminder pickers open in a popover below their button. If the button is low on the screen, the form first scrolls it up so a tall calendar is never cut off. An open popover doesn't block the editor behind it (the popover's UIKit pass-through views, since SwiftUI's `presentationBackgroundInteraction` only covers sheets): tapping another pill, such as **+ End** while the time is open, or **+ Location**, closes the popover and goes straight on in that one tap, with the next popover waiting until the last has fully gone (one presented while another is still leaving is dropped). Tapping the open pill again, anywhere else in the editor, or dragging the form closes it.
- Add one or more reminders in the item editor's **Reminders** section, which uses the same inline buttons as the schedule, tinted blue so reminders stand out; **+ Reminder** itself is a neutral grey button like **+ End**. It adds one (15 minutes before the start first, then another unused quick choice, or the next whole hour) and opens its popover: 0m / 5m / 15m / 30m / 1h before the start on one line, without a heading (VoiceOver reads 0m as “At start”) (each choice keeps its full label; the line wraps only at large text sizes) (or 9:00, 12:00 and 18:00 for untimed items), always all of them, even when some are already in the past, above an exact date and time. Quick choices leave the popover open. Each reminder shows as “15m before”, a time, or a day and time, with an ✘ to remove it. Reminders that have already passed are grey instead of blue and don’t notify. Reminders sort themselves by time shortly after a reminder's popover closes, with each button sliding to its new place (a native SwiftUI animation; immediate under Reduce Motion), and the section grows to show every reminder on as many lines as needed. The first reminder asks for notification permission. Notification titles use the item title; the body shows its planned day and time (including the end time for events), or Anytime and its live day, with no “Planned for” prefix (for example, “Tomorrow at 10:00 – 11:00 · in 30m”), followed by any deadline and a single “person • location” line without “With” or “At” prefixes. Multiple people or locations use commas, and missing fields leave no separator. Timed items append “in Nm” until their start, rounded up to a whole minute, or “now” at the exact start; reminders after the start omit the countdown. The countdown and Today/Tomorrow are relative to the reminder delivery date, not the date it was scheduled. Other dates include the weekday and calendar date. Past deadlines say “Was due”. Reminders are stored as a list; plans saved with the earlier single reminder load as a one-item list. A blue alarm button filters the selected day to unfinished items with an upcoming reminder; tap again to return. Filter buttons use separate circular glass controls with small orange/blue count badges. They fade and gently scale in and out over 0.32 seconds within one persistent toolbar host; the remaining control shifts smoothly into place. A button that is fading out after a day change ignores taps: its action checks the current day, since SwiftUI keeps a removed button tappable while it fades. Reduce Motion uses a short fade without scaling. Active filters use tinted native Liquid Glass with coloured icons; inactive controls are neutral. The bottom add and view-mode buttons use primary-colour icons. Filter icons are lighter and medium-weight, with a softer tint when active. The blue and orange filters are mutually exclusive. Both filtered views share the same status-and-action panel below each item: a small coloured symbol, a caption and a tinted action bar. Reminder status shows a blue alarm and the next upcoming reminder (or the latest past one), including its date when different from the viewed day, plus “· N reminders” when there are several; warning status shows an orange warning symbol and its reason. Reminder actions are Complete, Change time and Remove. Change time opens a focused date/time sheet; Change time and Remove act on the reminder shown and keep any others; removing the last one takes the item out of the filter without deleting it, and reminder edits/removal apply across a repeating series. Warning actions remain Complete, Leave open and Reschedule. A small blue dot marks items with an upcoming reminder; once every reminder has passed, the dot and the filter entry disappear. Completing an item removes it from the reminder filter, its count and its blue row dot, just like resolving a warning. Resolving the last item in the active filter returns to the full day, rather than showing an empty filter. Undoing completion restores it to the reminder filter; the saved reminder is retained.
- Choose **Repeat** → Every day, Every weekday, Every week, or Custom days in the editor (Never is the default). Work can repeat Monday–Friday with its start/end times, people, locations and reminder offset. Weekday/custom series start on the first matching date on or after the selected day. Each occurrence has independent completion/review state and stays on its scheduled day; repeating items do not carry over. The app uses two words for repeating items, everywhere: the **original item** (the master, the first day still in the series) and its **linked items** (every other day). If the original's day is deleted, the next day becomes the original item. Linked items stay linked after one in the middle is deleted. The editor's top line, above the title, says which one an item is:
- **Original item, linked to N items**: the exact total when the repeating item ends; otherwise the linked items up to and including today, as "so far", or "Original item, no linked items yet". The count comes from the repeat rule, since days are only generated as they are opened. Changes to the original (title, schedule, notes, people, locations, reminders and how it repeats) apply to all its linked items; each keeps its own completion. Moving it to another day shifts the series by the same number of calendar days, and choosing Never keeps only that day.
- **Linked item, linked to Gym, Thu, 29 Oct**: the original's name and date are a blue link. Neither line has an icon, nor do the carried lines ("Carried item, carried from …", "Original item, carried to …"). Tapping it closes the editor, switches back from a persona page if needed, moves the day view to the original's day (generating that day first if it was never opened) and opens the original there. VoiceOver reads it as a link.
- A linked item stays fully editable, including Repeat. Saving a change shows the alert **Unlink this item?** with **Unlink and Save**, **Edit Original Item** (which goes to the original as above, discarding the changes) and Cancel:
  - Other changes, or Never: "This item will be unlinked. The original item and other linked items won’t change. To change all of them, edit the original item." It becomes a single item and its day is kept out of the series. Keeping the same pattern never starts a second, identical series.
  - A new pattern: "This item will be unlinked and become a new original item, repeating every Saturday. The original item and other linked items won’t change." It becomes the original of a new repeating item from its day, and the old one keeps every other day, earlier and later. With X1–X4 weekly and X3 changed to daily, X1 stays the original of X2 and X4, and X3 becomes Y1, the original of Y2, Y3 and so on.

  Saving without changes just closes the editor.
- Completing, cancelling, and the reminder filter's Change time and Remove aren't edits in this sense. Completion and cancellation are per day, and the reminder actions still apply to the whole series. Deleting a repeating item asks which occurrences to delete (see Deleting). Older split series are reunited when edited. Future occurrences are generated as dates are opened, plus a rolling 60-day reminder window; the notification limit still applies.
- **Move to next day if unfinished** controls carry-over independently of the item’s time or duration. For a new item it follows the schedule until you set it yourself: Anytime items move forward, and giving the item a time turns it off (removing the time turns it back on). Existing items keep their setting.
- Add optional **Locations** and **People** in the item editor. Each section is one line of pills that you type in directly: every place or person is a filled pill with its icon and a remove button, and you tap its text to edit it in place. The dashed **+ Location** or **+ Person** pill turns into a new field with the keyboard up; Return or tapping elsewhere keeps it. Once something is typed, the dashed pill comes back beside the field, so tapping it keeps that one and starts the next straight away. A pill left empty disappears, and surrounding whitespace is trimmed. These are local text values; existing items open with none.
- Throughout the editor, add buttons (Add time, End, Reminder, Location, Person) are dashed outlines with grey text, so they never look like a value that is already set; set values are filled pills.
- **Save** keeps whatever is still being typed: it ends editing first, so a title, note, or a location or person typed into its new pill without pressing Return is saved too. With unsaved changes the sheet can't be swiped away: it stretches and springs back (`interactiveDismissDisabled`), and **Cancel** asks **Save your changes?** with **Save**, **Discard Changes** and Keep Editing (tap outside the dialog); without a title, Save isn't offered. With no changes, a swipe or Cancel closes the editor at once. SwiftUI has no hook for a blocked swipe, so the swipe itself doesn't ask; wrapping the sheet's UIKit presentation delegate would allow it, but was dropped to keep the editor native. Reordered or duplicate reminders don't count as changes. While an existing item has unsaved changes, a small **Edited** subtitle sits under “Your item” (`navigationSubtitle`); it goes away again if the changes are undone.
- Tap a circle to complete an item or undo completion. Completed items stay in place. Completion lives on the circle only; the item editor has no Mark complete button.
- Touch and hold an item, in the day view or on a persona's page, to lift it with **Cancel** and a red **Delete** option beneath. This is the native iOS lift: the row itself rises in place, with its own card and corners. Custom previews were tried and dropped. A separate copy made the system round it more and swap it in with a grey step on the way, and a preview shape on the row went grey the same way. The card has an opaque page-coloured backing under its faint tint, so the lifted row doesn't show the dimmed screen through it. That backing looks the same at rest, and the List/Time crossfade still reads cleanly with it.
- **Cancel** marks an item as called off without deleting it; held again, the menu offers **Uncancel**. A cancelled item stays in place in a quiet style: its circle becomes a faint ✘ outline and its title is struck through and fainter than a completed one, so done and called off are told apart at a glance. Tapping the ✘ restores the item rather than completing it, so a cancelled item is never ticked off by accident. VoiceOver reads it as cancelled, the circle as “Uncancel …”, and every row has a Cancel / Uncancel action. See Scheduling decisions for how it behaves.
- Pressing an item (anywhere but its circle) presses its whole card. The card settles to 98% size within 0.1 seconds, then springs back softly on release. It isn't shaded while pressed, so a hold goes straight into the system's lift without a grey flash. The title itself doesn't dim, so the item reads as one thing being pressed. Under Reduce Motion the card stays still. The button's press state reaches the card through the environment, since the card is drawn outside the button. Completion circles keep their own subtle dim while pressed. Tap a title to edit dates, times, notes, carry-over, people or locations. Reschedule through its Day field.
- Linked-item controls and parent/child labels are temporarily hidden. Existing relationships are retained in saved data for future work; deleting an item keeps the other items.
- Add a deadline in the item editor's **Deadline** section, below Reminders: one red pill with a flag, showing the time (and the day when it isn't the item's own), with an ✘ to remove it. **+ Deadline** sets it to the end of the item's time range, otherwise 17:00 on its day, and opens a date and time picker. An unfinished item with a deadline has a small red dot beside its review and reminder dots, including on its "Carried to …" entries; VoiceOver reads “Due …”. A red flag button beside the alarm and warning buttons filters the day to rows with a red dot, with a red count badge; its panel says “Due …” (“Was due …” once passed) with Complete, Change (opens the editor) and Remove. Deadlines don't notify. A repeating item's occurrences are each due as many days after their own day as the original is.
- Titles of completed and cancelled items share one light grey (`tertiaryLabel`), much lighter than an open item's; a "Carried to …" entry keeps the normal title colour while the item is unfinished. A row's small text (time, time left, people, locations, "Carried to …") uses that same grey, and so does the ticked circle.
- People and locations share one small, subdued line below the title, separated by a middle dot, without icons. Long details truncate visually; VoiceOver reads the full values and the editor shows every entry. Empty fields take no space.
- Items needing review have a small orange dot, alongside a blue dot when a reminder is set and a red one for a deadline. Dots show only in the full day: under a filter every row's panel already says why it is there, so no row shows any dot. Completion circles are neutral. The unused outline variant is retained for future use. The orange Liquid Glass button at the top right toggles a review filter in the same list, with complete / leave open / reschedule buttons under each item. Resolving an item removes it from the filtered list; an item left open keeps its orange dot in the full day. Tap the toolbar button again to return to the full day; resolving the last item does so too. The same list and item identities are retained while filtering: every row, section heading, the Past / In progress / Upcoming labels and the carried entries stay mounted, and a filter only collapses the ones it hides to zero height, so they fold away and open again in place within the same animation (rows that were removed and re-inserted used to appear at their final spot while their neighbours were still sliding back). Each timed row keeps its one shared time label under a filter too, centred on the row's first line through an alignment guide rather than on the row and its panel, so the label simply travels with its row instead of crossfading with a second copy. In Time view a collapsed row doesn't push later rows down, and the scale draws only the shown items. Each item's status panel is always present, collapsed and hidden outside a filter, so turning a filter on opens the panels below their rows and fades them in within the same half-second animation that moves the rows, rather than after it (immediately under Reduce Motion). A panel inserted only when filtering started had no earlier position, so the timeline layout put it at its final spot ahead of its moving row; that is why panels used to wait for the rows to settle. Panels keep the last filter's content while they collapse, and their action buttons are identified by position, so switching between the review and reminder filters relabels them rather than inserting new ones. Reduce Motion disables list movement. The toolbar uses only a warning symbol, with the count available to VoiceOver. Review dots, the toolbar warning, review reasons and actions share the same orange. Review actions sit in one subtle grouped bar with equally sized, equally weighted Complete, Leave open and Reschedule controls and fine separators; accessibility text sizes stack the controls. Changing day clears the filter. Ended time ranges and elapsed point times can prompt a review.
- Day content scrolls edge to edge behind the floating controls, with no navigation-bar background or top/bottom scroll-edge wash. Scroll content margins keep the first and last items reachable above the controls at rest. The bottom-left clock/list button switches between List and Time view and remembers the choice. Switching to Time view on today scrolls the current time to the middle of the screen alongside the rows' move, and today's page scrolls there too whenever it appears in Time view (on opening the app, or when it's built as a neighbour before being swiped to). Two things keep that scroll from being lost. Switching to Time view gives the content its full Time view height from the first frame (`reservesTimeHeight`) rather than growing with the rows. The scroll is also issued 50 ms after the switch: issued in the same update, or on the next run loop, the scroll view didn't have the new height yet. Whenever List view had been scrolled down, the scroll was then dropped and the timeline stayed where List view had been, which looked like every other switch. Opening a filter scrolls its topmost item (Anytime first, then by time) into the upper part of the screen, below the top controls, alongside the rows collapsing around it; Anytime rows carry ids for this (`anytime-…`), as Scheduled rows already did for the edge indicators. In Time view a filter doesn't change the height of anything above the timeline: the Anytime rows and the section headings it hides only fade (`FilterCollapse` with `keepsSpaceInTimeView`), so the timeline never moves when a filter opens or closes. Collapsing them, as List view still does, moved the timeline by Anytime's whole height, and closing a filter pushed what was on screen away. A Scheduled row hidden by a filter waits where it will appear, after the shown rows above it, without pushing later rows down; at its bare time it slid across the other cards when the filter closed. The hour labels are one tall asynchronous canvas, but each item's dot and duration bar is a small view of its own (`TimelineTrack`) that stays in place: a filter fades the tracks it hides, the review filter fades a track to orange, and ticking an item off fades its track to the lighter grey over 0.35 seconds once the completion reaches the store. The connector from the track to the card fades in the same frames: it's drawn at full strength and dimmed as a view with the track's animation, since a colour change inside its canvas switched in one frame, ahead of the track. Drawn in a canvas, all of these changed in one frame. Swapped or inserted, they changed in one frame, because the page is hosted and the filter's animation only reaches views that stay and animate (the timeline's background carries its own `.animation(value: filter)` for this). For the scroll to now, the scroll target is a 1-point view of its own below a spacer, since scrolling to a padded or offset view finds the top of the timeline instead. A shared SwiftUI scroll surface and the same item views slide and spread from their compact positions into the timeline over half a second, without a separate List cell resizing underneath, while the scale and connectors fade in; switching back reverses the movement. Each item keeps two measured title layouts at fixed widths and crossfades between them as its position moves, avoiding per-frame text reflow. The two layouts blend additively, so matching text stays fully opaque instead of dimming halfway. They blend that way only while switching (`ViewMode.switching`): rows blended additively that slid in from off screen, as when a filter closes up the list above the Scheduled section, stayed undrawn until the slide ended and then popped in. Measurements are cached across animation frames and only redone when displayed content, order, filter or text size changes. In the full-day view, one shared time label remains visible throughout the switch, moving with the row without crossfading or changing width. At rest each row draws its own time, so the time behaves exactly like the title (for instance when the row is held and lifted), and the row hands it to the shared label only for the 0.6 seconds a List/Time switch takes (`ViewMode.switching`). The two are laid out in the same place, so the hand-over doesn't show; the title layouts reserve its space, and review/reminder dots travel with that label. While switching, the cards also drop the opaque page-coloured backing they keep at rest (`itemCardUnbacked`): mid-move a row's List and Time copies sit apart, and their additively blended backings painted white blocks over the timeline scale between the items. The toggle icon morphs between clock and list symbols. Only the active variant accepts taps, appears to VoiceOver and produces completion feedback. The fixed-size timeline scale and connector curves use their final timeline geometry and fade into place. Both rasterise asynchronously off the main thread, and the current-time marker is a separate small view, so revealing Time view never stalls on drawing the full-day scale and minute updates never redraw it. There are no per-frame row-anchor preferences or connector redraws while items move. A single animation drives row movement, content height and timeline visibility, including interrupted switches. The List/Time choice lives in a small observable model read only by the views that move or fade, so switching never rebuilds the day's content; neighbouring day pages follow 600 ms later. The app opts into ProMotion (`CADisableMinimumFrameDurationOnPhone` in `Timo/Info.plist`), and each switch briefly runs a display link requesting 120 Hz so the SwiftUI animation is not capped at 60 Hz. Reduce Motion changes the layout immediately; with Reduce Motion's Prefer Cross-Fade Transitions option, the layouts dissolve instead, and day changes (chevrons, calendar or swipe) dissolve rather than slide. Time view keeps natural item heights, with hour labels down the side, fine connectors to the scheduled times and narrow duration strokes. There's no axis line or hour ticks: the hour labels and the items' tracks are the timeline. A rail beside the tracks read as one more track. Every item's dot and duration bar sits on a track right of the hour labels, each bar a plain stroke without an end tick, and items that overlap get further parallel tracks (a second, third and so on), each bar extending only over its own duration; longer events sharing a start stay closest to the hour labels. A point task takes a track too, occupying about four minutes (its dot's height), so a task inside a meeting or at the same time as another task moves aside instead of sitting on top of it. Tracks are reused once an event ends (`TimelineLanes.assign(starts:ends:)`). Gaps follow a one-point-per-minute scale; simultaneous/nearby items stack without overlapping and keep their exact timeline anchors. A current-time marker appears for today. The part of the timeline already passed is shaded with a faint grey wash from the middle of the first track to the right edge of the screen, from the top of the timeline down to the current time, so the hour labels stay on the page colour and the timeline itself seems to fill up; cards keep their opaque backing, so they stand clear of it. The current time itself is a hairline across, starting at a dark pill in the hour column that holds the time (“18:45”); the hour label within 15 minutes of it is left out, so it doesn't peek out beside the pill. A faint dashed line, and later a plain bold label, were both too easy to miss. Hour labels already passed are dimmed to tertiary. Every open item's track is the same grey, before and after now; finished, cancelled and carried items' tracks are lighter. The elapsed part of a track used to darken, but with the shading already marking time passed it only made past and upcoming items look different. The completion circles still trace an item's time. Reminders and deadlines appear only with their filter open: with the blue reminder filter, each of an open item's reminders on that day is a blue dot on the item's track at the reminder's time, with a blue curve to the item's card; with the red deadline filter, its deadline is a red dot joined the same way. The curves end at the middle of the card, like the item's own connector, rather than running along the track to its start. They are laid out with the cards (`TimelineMarkConnector`, which carries its dot) and stay laid out while hidden, only fading, so they move with the rows when a filter opens or closes; inserted and removed, a fading one stayed behind as the rows moved. With the orange review filter, an item to review lights its whole track and start dot orange, fading from grey. They used to show all the time; tying them to the filter keeps the tracks quiet otherwise. For items already shown on the day, the filters, badges and row dots include any upcoming reminder or open deadline, even when it falls on another date; the status panel includes that date so configured reminders and deadlines remain visible. A reminder or deadline belongs to the day it falls on: an item's blue or red dot, and its place in the reminder or deadline filter, are on that day only. An item planned for today whose reminder is tomorrow has no blue dot today and isn't in today's reminder filter; it's in tomorrow's, as a visitor, and the same goes for deadlines. So the reminder and deadline filters also bring in items from other days: an unfinished item whose upcoming reminder, or whose open deadline (passed or not), falls on the viewed day is shown there under that filter, as a visitor (`PlanItem.visits`, `Planner.visitingItems`). Its card has no fill and a dashed outline, so it's clear it isn't planned for this day; a timed visitor's time already names its own day (“3 Nov · 10:00”), and an Anytime one says “Anytime, Fri 30 Oct” under its title. The Anytime rows are laid out like the Scheduled ones: the same layout (`DayTimelineLayout` with `compactOnly`), the same pair of List and Time view copies per row with the same modifiers, and one compositing group with an empty asynchronous `Canvas` behind it, as the timeline scale and connectors are behind Scheduled. That canvas has SwiftUI render the group off the main thread; without it, as plain rows, a filter animation on a day of Anytime items dropped a frame several times a second on a phone while Scheduled stayed smooth.
- Each item sits on its own card: a slightly rounded rectangle (12-point continuous corners) in a very light tint of the text colour (2.2% opacity, 7% with Increase Contrast, over an opaque page-coloured backing) with a half-point outline in the same colour as a carried entry's stroke, so it works in light and dark mode. The cards are inset 16 points from the screen edges, with a 6-point gap between them. The same card is used in List and Time view, on carried entries and on persona pages. A status panel opened by a filter sits inside its item's card. In Time view, connectors end at the card's leading edge, and the shared time label keeps the card's 12-point trailing inset.
- Rows use a compact layout with times on the right, vertically centred against the full title and detail block; longer titles and larger text sizes wrap naturally. Tap a title to edit or delete, and use its circle to change completion. There are no row swipe actions. Deleting an item leaves other items intact.
- The bottom-centre glass date control shows the full weekday above the date. When viewing today, a soft cyan/blue/violet/pink halo uses matching 1.6-second fades on arrival and departure, easing gently at both ends. The halo itself is still: constant decorative motion distracts and kept the GPU compositing while idle on today. Its brightness stays steady and subtle, without breathing or random variation. Three blurred layers create a luminous core and diffuse spill beyond the capsule, behind the glass rather than a sharp coloured outline. The same glow remains mounted so rapid day changes reverse the fade from its current brightness. It disappears on other days and appears without a fade under Reduce Motion. The blurred ring is a mask drawn once per size over a static conic gradient, so the halo costs no frames once shown (an earlier version redrew the blurred gradient on the main thread at about 9 ms per frame and made view switches hitch on today). The glow never intercepts taps or swipes; the top of the list only shows completion/filter information. A quiet relative date label appears above the control on opening and when changing days, then fades after 1.5 seconds, or as soon as a press on the date starts (the pressed glass would otherwise swell into it). It sits in a small glass pill so the list scrolling behind it never makes it hard to read. It shows Today, Tomorrow, Yesterday, just Next or Last within seven days (the control already names the weekday), or a day count further away. Repeated navigation restarts the display time without queuing labels; VoiceOver always includes the relative date. Use the date control: tap or pull upwards to open the calendar. The glass date capsule itself stretches up into a glass calendar card and folds back into the capsule when it closes, as one piece of Liquid Glass, instead of zooming into a separate sheet. The capsule and calendar are one glass view: a single spring grows its frame from the capsule's size to the calendar's, and both contents are clipped to it. The calendar never scales or moves; it sits at full size with its bottom on the capsule's and is uncovered as the glass grows, so it can't drift from the glass beneath it (an earlier version morphed an empty glass shape with `glassEffectID` and scaled the calendar on top on a separate timing, which never quite lined up). The weekday and date fade out as the glass starts to grow and back in as it finishes folding; the calendar fades in just after them, only so it doesn't show through the capsule. Fades are scoped to opacity, so the contents' positions always follow the glass's spring. The glass keeps a fixed 28-point corner radius rather than a capsule shape, so it never swells into a circle on the way; the halo and relative-date pill stay capsule-sized behind it. The view and add buttons step aside while the calendar is open. Choosing a day folds the calendar away after a brief moment, so the new selection is seen; tapping the day that's already selected, tapping outside or pulling it down also closes it. A small glass **Today** button floats just above the open calendar, outside its glass so the calendar keeps its size; it rides the top edge as the glass grows, goes to today and folds the calendar away like picking a day, and leaves as soon as the calendar starts to fold. The calendar is UIKit's `UICalendarView` with multi-date selection kept to exactly one day: a graphical DatePicker and single-date selection both ignore a tap on the selected day, while multi-date selection reports it as a deselection, which is treated as choosing that day again. The viewed day is a black circle and today is a blue number, from the calendar's blue tint (a black circle when today is the viewed day). Today used to be added to the selection as well, which drew it as the same black circle as the viewed day, and with a label-coloured tint UIKit doesn't mark today at all; calendar decorations would have added a row under every date. With Reduce Motion the glass changes size at once and only the contents cross-fade. For smoothness on device, the calendar stays built while hidden (creating the system calendar view mid-animation stalled the opening frames) and is laid out at its own width whatever the glass's size, so the morph never makes it lay out again; opening or closing runs a short 120 Hz display link like the List/Time switch. From opening until the glass has folded back, the day pager holds off refreshing its page and building the neighbouring days (picking a day used to build them mid-fold and made it stutter); the chosen day's own page is swapped in during the brief pause before folding, and the neighbours are built once the fold has finished. Picking a day records it in the calendar at once, so the calendar isn't updated again while it folds. The halo returns once the calendar has closed; hold to return to today as soon as the 0.35-second press is recognised, as quick as the persona button's menu (without waiting for release), swipe left for the next day or right for the previous day. Horizontal swipes change one day per gesture with a directional page slide (no movement with Reduce Motion); once a horizontal drag is recognised, the pages' vertical scrolling for that touch is stopped and their scroll indicators are hidden at once until the pages settle, so none slides across the middle of the screen. The indicator only runs between the top controls and the dock, never under the glass, so no scrollbar slides across the middle of the screen; a deliberate upward pull opens the calendar on release, allowing the glass press to finish first; downward or short drags do nothing. VoiceOver exposes the same actions. The top calendar/Today buttons have been removed. The dock observes swipes simultaneously with the central date’s hold gesture, so a stationary hold can fire before release. The chevrons are tappable previous/next buttons, and the date control uses native interactive Liquid Glass feedback, without a custom positional offset. Short horizontal swipes (six points) register a day change; repeated swipes immediately interrupt the current slide and move to the next selected day, without queuing. Swiping left or right anywhere on the day’s content also moves to the next or previous day, in both List and Time views, including empty days. A direction-gated pan recogniser tracks horizontal drags, cooperates with both UIKit and SwiftUI recognisers, and rejects vertical gestures before recognition. The current page and adjacent days move with the finger; release completes the remaining slide according to distance and projected momentum, or eases back for a short drag. Dragging the date capsule drives the same pager and retains its six-point navigation threshold. The current page and its two neighbours are retained and laid out while idle. The visible neighbour becomes the selected page after settling, preserving its existing text and scroll layout. No full-screen snapshots or destination-page reconstruction occur on release. Content updates are deferred during motion and keyed to plan, filter, mode, accessibility size, safe-area and minute changes, so dock and relative-label updates do not rebuild hosted pages. Only the foreground page animates; cached neighbouring pages disable implicit animations and update after the list/time morph finishes. Recognised horizontal drags synchronously suppress opening, completing and filtered-row actions through settling and for at least 0.2 seconds after release, including cancelled or too-short drags, so SwiftUI cannot also fire the item’s button action, or open Settings from the link at the bottom of the day. Ordinary taps and vertical scrolling remain available; the floating date control retains its own gestures. Day changes settle with a damped 0.28-second UIKit slide from the actual drag position. Interrupted transitions retain their presentation-layer position, and data reconciliation is published after settling. Reduce Motion changes days immediately. SwiftUI list filtering does not control the page animation; the add button remains at the bottom right.

## Personas

Personas are the different focuses in a life: **Health**, **Work**, **Family**, **Friends** and **Personal**. Each has its own gradient orb (mint–green, cyan–blue, yellow–orange, pink–red, purple–indigo).

- The glass capsule in the top left shows the current persona with its orb. It starts on **All**, a blend of every persona's colour, which is the normal day view.
- Tap the capsule to open the persona menu, which grows out of it as a Liquid Glass list: All, Health, Work, Family, Friends and Personal, each with its orb and a checkmark on the current one. Choose one to switch to it. VoiceOver reads the capsule as "Persona" with the current choice; the menu is the system one, so it reads naturally too.
- Switching persona cross-fades: the day view and the persona pages fade into each other, so each page's gradient wash blends into the next rather than sliding across. The capsule's label changes at once, and the menu folding back into it is the only motion. On a persona page, swiping left or right anywhere on the page cycles through the personas (left for the next, right for the previous), with the same cross-fade. A swipe that starts on an item never opens or completes it: the persona swipe shares the day pager's gate, which holds off item actions during the drag and for 0.2 seconds after. It wraps from Personal back to Health and never lands on All; going back to All is done from the menu. The swipe only starts for a clearly sideways drag, so vertical scrolling is untouched. VoiceOver users swipe up or down on the capsule for the same cycling (from All, up starts at Health and down at Personal). On All, horizontal swipes still change the day.
- Choosing a persona swaps the day view for that persona's history: every item in that persona (including items that are also in others) grouped by day, newest day first (Tomorrow, Today, Yesterday, then weekday and date), under a small "x/y complete" line like the day view's. The page doesn't repeat the persona's name or orb; instead the top-left button's glass takes on the persona's colour while one is chosen, the same light tint the review and reminder filter buttons show when they're on. The tint switches at once with the label, so it never lingers after going back to All. The day view stays loaded underneath, so going back to All returns to the same day instantly. The review and reminder filters rest while a persona is shown, because they belong to a single day.
- Each day on a persona page lists what that day's list shows of the persona, with the day list's own rows (time ranges, people and locations, progress circles, time left, review and reminder dots) in the same order: untimed and carried items first, then by time. Besides each item's own day, Today is listed whenever today's list shows one of its items, such as a range still running; such an item is counted once. In the history, tap a circle to complete an item or tap the item to edit it. **+** adds an item for today that already has the persona.
- The item editor keeps its explanations out of the way: each section title (Persona, Repeat, Carry over, Reminders, and Schedule for a carried item) has a small (i) that shows or hides that section's explanation, which appears beneath the section's content. They start hidden.
- In the item editor, the **Persona** section shows the five personas, each with its orb. An item can be in several personas, or none: tap a persona to add it (it takes a light tint of its colour, like a reminder pill) and tap it again to remove it. With nothing highlighted, the item has no persona. An item in several personas is listed on each of their pages.
- As in the day list, a carried-over item is shown as itself on the day it is shown (today, or the day it was completed), and every day it was carried on from keeps its quiet "Carried to …" entry in its original place. A repeating item shares its personas across all its occurrences, and every linked item generated so far is listed, including those ahead of today (about 60 days are generated ahead), as are non-repeating items planned for later days.
- The set of personas is fixed for now. Adding, renaming or recolouring them is not built yet.

## Deleting

- Holding an item opens the system context menu. The rest of the screen dims, so it's clear which item is held. The item rises as one card, grown to show its history in small grey text under its details ("Created 29 Oct, 10:58", then "Completed …" or "Cancelled …", each on its own line, with the year only for another year), and Cancel (or Uncancel) and Delete sit beneath. The lifted card is a copy of the row drawn at the row's width, because a timed row in the day view draws its time label and dots outside the row (the shared label that moves between List and Time view), and the copy draws its own. The copy lays the time out in the same fixed column as the shared label, so lifting moves the same layout rather than cross-fading to another, which used to flash. iOS draws the lift from the row before the card appears, and the shared label stays covered for a while after the card has settled back, so without this the time vanished briefly on the way out. A Liquid Glass `Menu` growing out of the item was tried and dropped. It didn't show which item was held, it covered most of the row, iOS hid the title it grew from, and its UIKit layer broke the additive blend of the List/Time row copies, which drew timed rows blank in light mode. A card that expanded in place, with its own Cancel and Delete buttons, was tried too and dropped in favour of the glass menu. System button styles and menus inside a row break that same blend.
- Every item has the same **Delete**: in its long-press menu, and as **Delete item** at the bottom of the editor. A single item is deleted straight away, from the menu and from the editor alike, with no confirmation, since the Undo that follows covers a mistaken tap.
- For a repeating item, Delete carries the system's chevron and opens its choices within the same menu (a native submenu), from narrowest to widest as Calendar does: **This linked item only**, **This and following linked items**, and **Original and all linked items**, in red. On the original item they are **Original item only** and **Original and all linked items**. Delete is always fully red, like a single item's Delete: bin, title and chevron. SwiftUI can't give a submenu the destructive role, so the bin is a red image kept in its own colour, and `Timo/DestructiveSubmenu.swift` does the rest in UIKit. It answers UIMenu's `options` with `.destructive` for submenus titled Delete, which reddens the title, and tints the row's chevron red when the row lays out, since iOS draws it in the label colour even then. The row is a private UIKit view (`_UIContextMenuCellContentView`); if a later iOS renames it, only the chevron goes back to black. The editor's **Delete item** has a red bin and red text and, for a repeating item, opens the same choices as a menu from the button.
- Deleting the last item of a section (or of the day) takes the section away in 0.15 seconds, and the “Nothing planned” line fades in just after, instead of the section fading out over the list's half-second animation underneath it. The item editor stays “Your item”, with its Delete row, while it closes after a deletion.
- Every deletion can be undone. A small Liquid Glass capsule appears above the dock, on the day view and persona pages alike, reading Deleted “title” with an **Undo** button, like Mail's Undo Send. It stays 5 seconds (10 with VoiceOver, which also announces it) and fades as glass does. The system's own undo works too: shake, or the three-finger gestures, offer Undo Delete. Undo puts back exactly what the deletion removed: the items with their IDs and completion, the repeating plans as they were (a deleted occurrence's excluded day, an ended series, a removed series), and links to children. Anything changed since then stays as it is. After Undo from the button the system's undo has nothing left to do.
- This linked item only (or Original item only): its day is kept out of the series (its excluded days), so it isn't generated again, also after the original item is edited. The other items keep their completion and cancellation; deleting the original item makes the next day the original.
- This and following linked items: the series ends before that day, and items from that day on are removed; earlier ones stay as they were, with their completion. Older plans that split a series into several parts are handled as one: parts starting on or after that day are removed and the others end before it.
- Original and all linked items: the series and every item in it, past and future, are removed.
- Deleting never deletes other items; a deleted item's linked children are kept and unlinked.

## Scheduling decisions

- One item model with a local day, optional start time, optional end time, completion and an independent carry-over preference. There is no stored task/event type in the new format.
- Calendar.current determines local days, including across daylight-saving transitions.
- An item's scheduled day never changes on its own. An unfinished item with carry-over enabled is shown on today as an untimed item with a "Carried from" line, until it is completed; its scheduled day and time stay as planned. A time range that is still running stays on its own day until it ends.
- Ticking an item off while viewing a past day records it as done on that day (at the current time of day). A carried item completed that way is shown completed on that day and no longer on the days after it, so an event added after the fact can be ticked off on the day it actually happened. Ticked off on today or a future day, it counts as done now.
- Where an item is shown is worked out from its scheduled day, its completion and the current time, so nothing has to run at midnight; the view follows the day as it changes.
- Items with carry-over disabled, completed items and future items are shown on their scheduled day only. Repeating occurrences never carry.
- Every day from a carried item's scheduled day up to the day it is shown on keeps a quiet "Carried to …" entry. These entries are not counted towards completion or reminded about again; ticking one off completes the item on that day. Each entry stays in the item's original place rather than in a block below: on its scheduled day a timed item keeps its time among the Scheduled items (and on the timeline in Time view), otherwise it sits among the Anytime items. It uses the normal row and card (same fill as every other item), with a › circle, the normal title colour while unfinished and the "Carried to …" line. While the item is unfinished the entry keeps its small orange dot, so an earlier day still shows what was left open there, and the entry is counted in that day's orange review filter, whose panel says “Unfinished, carried to …”; Leave open takes it out of that filter but keeps the dot. It has no blue reminder dot. A filter keeps an entry when the entry has that filter's dot (orange review, red deadline) and hides it otherwise.
- Rescheduling an item moves its trail with it: planned for a later day, the earlier days let it go. Plans saved before this (when carrying moved an item's day to today) are restored to their scheduled day once on opening, with time ranges shifted back; a single time that was dropped when it moved cannot be recovered.
- Past days otherwise contain the items still scheduled there, not a snapshot of the original plan. No historical copies are generated.
- Time ranges appear on every day they overlap; ending at midnight excludes the following day.
- Changing a start time or day preserves an existing duration. Removing the start time also removes the end time.
- Stored parent relationships are preserved, but linking controls and parent completion suggestions are temporarily disabled in the interface.
- Time-passed suggestions never change completion state. Leave open dismisses the suggestion until the schedule changes or completion is undone: the item leaves the review filter and its count, but keeps its orange dot while it is unfinished (VoiceOver reads “Left open”). A carried item is not flagged for its old time.
- Cancelling is a state of its own, separate from completion (`cancelledAt` beside `completedAt`), and the two never stand together: cancelling clears completion, and uncancelling leaves the item open. A cancelled item doesn't carry on: like a completed one, it stays on the day it was cancelled from (a past day when cancelled while viewing it, otherwise today), with the usual "Carried to" entries on the days before. It never needs review, shows no time progress or "in 25m" note, and isn't in the reminder filter; its reminders are kept but don't notify, and come back if it is uncancelled. The "x/y complete" counts leave cancelled items out of the total. Rescheduling or editing a cancelled item keeps it cancelled.
- Cancelling a repeating item cancels only that occurrence, like completion; editing the series keeps each occurrence's cancellation, and new occurrences start uncancelled.
- Parent selection enforces one level of linked children and rejects missing parents and cycles.
- The screen follows today across midnight when viewing today; intentionally viewing another day does not jump back.

## Persistence

The plan is stored as an atomically written, versioned JSON document, Timo/plan.json. With the App Group `group.com.timovijn.timo` it lives in the group's shared container, so the lock screen widget can read it; a plan saved earlier in the app's own Application Support moves there once, at launch. Without the App Group it stays in Application Support/Timo/plan.json (`Timo/PlanLocation.swift`). The plan is small and local; this keeps version one dependency-free and allows scheduling tests to run without an iOS runtime. SwiftData is not used in this implementation. A later storage migration can retain the existing item IDs.

The version 7 format stores each item's personas as a list (also on repeat templates), in a fixed order. It reads existing version 1–6 plans without changing item IDs or schedules: version 6 kept a single persona, which opens as that one; older plans open with none. Personas this version doesn't know are left out. Repeat templates were added in version 5. A cancelled item stores `cancelledAt`; the key is only written for cancelled items and older plans open with nothing cancelled, so it didn't need a new version.

### iCloud

**Sync with iCloud** in Settings keeps the plan in the person's private iCloud database (CloudKit, `CKSyncEngine` in `Timo/CloudSync.swift`), as a backup and so it's the same on each of their devices. It's off until turned on. There is nothing to sign in to in the app: it uses the iCloud account the iPhone or iPad is signed in to, and without one the section says so with a button to the Settings app; signing in there takes effect when the app returns to the foreground. The section shows Checking, Syncing, "Up to date · synced 2 minutes ago", or what went wrong in orange. Signing out of iCloud, switching accounts, or deleting the app's data from iCloud turns sync off and says why; the plan always stays on the device, and turning sync off leaves the iCloud copy as it was.

The JSON file stays the local copy. Each item and repeating plan is one record in a "Plan" zone, holding the value as the same JSON (record types `Item` and `Series`, field `payload`), so records follow the app's own format and migrations rather than a CloudKit schema of their own. Every save queues what it changed (`PlanStore.commit` compares before and after); changes fetched from iCloud are written back through `PlanStore.applyFromCloud`, which doesn't queue them again. Turning sync on for the first time uploads the whole plan; a second device's own items are kept alongside. The engine's state and, per record, its system fields and the value iCloud last had live in Application Support/Timo/sync.json, removed when sync is turned off. The app has the iCloud (CloudKit, container `iCloud.com.timovijn.timo`) and push entitlements (`Timo/Timo.entitlements`) and the remote-notification background mode, so other devices' changes arrive without opening the app. A free (personal) developer team can't sign those, so the `TIMO_ICLOUD` build setting decides whether a build has them: YES for the Simulator, NO for devices until the team is a paid Apple Developer Program membership. With NO, the build has no entitlements and Settings shows no iCloud section (creating a CloudKit container without the entitlement would crash); to turn it on, set `TIMO_ICLOUD = YES` for the Timo target in both configurations, which also points `CODE_SIGN_ENTITLEMENTS` at the entitlements file.

When two devices change one item, the edits are combined field by field (`PlanItem.merged(base:mine:theirs:)`) from the version both started from: whatever this device changed wins, everything else comes from iCloud. The schedule (day, start, end), completion with cancelling, and the repeat pattern are each taken as one, so a merge never pairs one edit's start with another's end. A change still waiting to be sent is merged with a fetched one and sent after it. Repeating plans and deletions aren't merged: the latest wins, and an item deleted on one device is deleted everywhere.

A repeating item's occurrences get their ID from the series and the day (`PlanItem.occurrenceID`), so two devices generating the same days produce the same records rather than doubles. When an occurrence shifted or detached by an edit already holds the derived ID, a new one falls back to a random ID. Occurrences saved before this kept random IDs, so after a sync one day can arrive twice; `Planner.mergeDuplicateOccurrences` folds them into one, choosing from the IDs alone so every device keeps the same copy, passing on a completion and moving children over.

Sharing single items with other iCloud users comes next. It's planned as one zone per shared item, shared as a whole; a repeating item shares its whole series. One person ticking a shared item off completes it for everyone, while `PersonalDetails` (reminders, personas, a dismissed review) stays each person's own.

Messages name the device ("this iPad" or "this iPhone"); the sync itself doesn't depend on it, so an iPad on the same account is just another device. Still to check by hand, once on a paid team: sync between two signed-in devices, such as an iPhone and an iPad, which the Simulator can't show without an iCloud account. Before a TestFlight or App Store build, the CloudKit schema (created by the first development sync) has to be deployed to production in the CloudKit Console.

Writes complete before in-memory state is published. Save failures are surfaced. An unreadable or unsupported existing document is left untouched and saving is disabled. Deleting the app deletes its local plan. There is no backup/export UI yet.

## Reminders

Local notifications are scheduled after a successful save and refreshed at launch or foreground entry. Completion, cancelling, deletion, disabling a reminder and time edits update pending notifications; notifications also present while the app is open. Notification delivery must still be checked on the iPhone, including permissions and Focus settings.

The nearest 64 future reminders are scheduled, replenished on subsequent saves or app entry. Reminders that have passed are never repeated for a carried item. Each reminder is its own notification. Changing an existing start shifts all its reminders by the same amount; changing an untimed item's day shifts them by calendar days. Removing an item's start preserves its explicitly set reminders.

## Lock screen widget

The **Today** widget (`TimoWidget/`) shows how many of today's items are done, the same count as the day view's "x/y complete" (`DayProgress` in the model): cancelled items aren't counted, and carried items count on the day they're shown. It comes in two lock screen sizes: a ring with "3/5" in the middle, filling as items are done (a checkmark when nothing is planned), and a line above the clock, "3 of 5 done" ("Nothing planned" on an empty day). VoiceOver reads "3 of 5 done today".

It reads the plan from the App Group's shared container. Every save reloads it; otherwise its timeline changes when a running range ends and at midnight. Like iCloud, the App Group is only switched on for the Simulator for now (`TIMO_ICLOUD`), since the free Personal Team may not support it; on a device the widget shows "Open timo" until it is.
