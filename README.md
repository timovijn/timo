# Timo

A native, local-first iPhone and iPad daily planner built with SwiftUI. Requires iOS 26 or later and a compatible Xcode installation. There are no third-party dependencies, accounts or network requests.

The display name is **Timo** for the app and widget. The app icon is the approved rotated T on charcoal: its checkmark strokes are ivory and its lower-right arm is muted warm grey, supplied as an opaque 1024 × 1024 universal iOS icon in `Timo/Assets.xcassets/AppIcon.appiconset`; the asset catalog is included in the app target's Resources phase and selected for both Debug and Release builds. The approved artwork is `generated_images/exec-228f1abb-adaa-40cc-836d-4f956cb7d9fb.png`; the source monogram is geometrically centred with equal opposite margins. Original artwork and explorations are retained in `generated_images/`.

## Run on your iPhone

1. Open **Timo.xcodeproj** in Xcode (not Package.swift).
2. Select the **Timo** project in the left sidebar, then the **Timo** application target.
3. Under **Signing & Capabilities**, leave **Automatically manage signing** enabled and select your **Personal Team**. If the bundle identifier is unavailable, change `com.timovijn.timo` to a unique identifier.
4. Connect your unlocked iPhone, trust the Mac and enable Developer Mode if prompted.
5. Select your iPhone as the destination beside the Timo scheme and press **⌘R**.

A free Personal Team can install the app on your phone. You must run it again from Xcode when its seven-day provisioning profile expires. Keep the same bundle identifier and update the installed app rather than deleting it to preserve its local data.

## Run in Simulator

Open the same project, select an installed iPhone Simulator as the destination and press **⌘R**. No signing team is needed for Simulator. If a runtime is missing, install it through Xcode Settings → Components.

## iPad

The app runs natively on iPad in every orientation, so it also works in Split View and resizable windows. The layout is the iPhone's: the day list, time view and persona pages keep their rows to a reading width of 680 pt, centred, while swipes still work across the whole screen; the dock's buttons stay in the corners and the calendar keeps its 380 pt width. The editor and other sheets open as centred form sheets. On iPhone the screen is narrower than that width, so nothing changes there except in landscape on the largest phones.

## Try the first version

- An empty day shows only a quiet “Nothing planned” line; the add button in the dock starts it.
- Tap **+** to create an item with a title and day. The title wraps visually but never contains line breaks: Return (labelled Done) closes the keyboard, and pasted line breaks become spaces. Tapping anywhere outside a text field, or opening a schedule or reminder popover, also closes the keyboard; the tap still reaches whatever it landed on. The Schedule section is one line of inline capsule buttons: the day, **Add time**, and, once a time is set, **+ End**. The day reads Today, Tomorrow, Yesterday or a weekday within the coming week, otherwise a short date; its popover offers Today / Tomorrow / Next week above a calendar and closes on a choice. Schedule popovers always open below their button (arrow on top) at a fixed width, so the calendar is never squeezed beside the leftmost button. **Add time** picks a start after the day’s last timed item and not before now (rounded up to a quarter hour; the next whole hour today when nothing else is planned; otherwise 9:00) and opens a popover with that suggestion, 9:00, 12:00 and 18:00 above a time wheel. **+ End** opens duration choices (15m, 30m, 45m, 1h, 2h) on one evenly divided line (wrapping only at large text sizes; VoiceOver reads full durations) above an exact end date and time. A duration sets the end time and leaves the popover open so the end can be checked or fine-tuned. The button shows the end time itself: “until 10:30”, or “until Saturday, 10:30” on a later day; and the end can only be after the start. Set times carry an ✘ inside the capsule (with a 44-point tap target); removing the start also removes the end, but the duration is remembered while the editor is open and comes back when a time is added again. Buttons animate in and out (immediately under Reduce Motion), adding or removing a value gives a selection haptic, and the capsules wrap at large text sizes. VoiceOver reads them as Day, Time and End time with full values (for example “Ends 29 Oct 2026 at 11:00, 1 hour”), Add time / Add end time, and Remove time / Remove end time. There is no Task/Event selector.
- Schedule and reminder pickers open in a popover below their button. If the button is low on the screen, the form first scrolls it up so a tall calendar is never cut off. An open popover doesn't block the editor behind it (the popover's UIKit pass-through views, since SwiftUI's `presentationBackgroundInteraction` only covers sheets): tapping another pill, such as **+ End** while the time is open, or **+ Location**, closes the popover and goes straight on in that one tap, with the next popover waiting until the last has fully gone (one presented while another is still leaving is dropped). Tapping the open pill again, anywhere else in the editor, or dragging the form closes it.
- Add one or more reminders in the item editor's **Reminders** section, which uses the same inline buttons as the schedule, tinted blue so reminders stand out; **+ Reminder** itself is a neutral grey button like **+ End**. It adds one (15 minutes before the start first, then another unused quick choice, or the next whole hour) and opens its popover: 0m / 5m / 15m / 30m / 1h before the start on one line, without a heading (VoiceOver reads 0m as “At start”) (each choice keeps its full label; the line wraps only at large text sizes) (or 9:00, 12:00 and 18:00 for untimed items), always all of them, even when some are already in the past, above an exact date and time. Quick choices leave the popover open. Each reminder shows as “15m before”, a time, or a day and time, with an ✘ to remove it. Reminders that have already passed are grey instead of blue and don’t notify. Reminders sort themselves by time shortly after a reminder's popover closes, with each button sliding to its new place (a native SwiftUI animation; immediate under Reduce Motion), and the section grows to show every reminder on as many lines as needed. The first reminder asks for notification permission. Notification titles use the item title; the body shows its planned day and time (including the end time for events), or Anytime and its live day, with no “Planned for” prefix (for example, “Tomorrow at 10:00 – 11:00 · in 30m”), followed by any deadline and a single “person • location” line without “With” or “At” prefixes. Multiple people or locations use commas, and missing fields leave no separator. Timed items append “in Nm” until their start, rounded up to a whole minute, or “now” at the exact start; reminders after the start omit the countdown. The countdown and Today/Tomorrow are relative to the reminder delivery date, not the date it was scheduled. Other dates include the weekday and calendar date. Past deadlines say “Was due”. Reminders are stored as a list; plans saved with the earlier single reminder load as a one-item list. A blue alarm button filters the selected day to unfinished items with an upcoming reminder; tap again to return. Filter buttons use separate circular glass controls with small orange/blue count badges. They fade and gently scale in and out over 0.32 seconds within one persistent toolbar host; the remaining control shifts smoothly into place. A button that is fading out after a day change ignores taps: its action checks the current day, since SwiftUI keeps a removed button tappable while it fades. Reduce Motion uses a short fade without scaling. Active filters use tinted native Liquid Glass with coloured icons; inactive controls are neutral. The bottom add and view-mode buttons use primary-colour icons. Filter icons are lighter and medium-weight, with a softer tint when active. The blue and orange filters are mutually exclusive. Both filtered views share the same status-and-action panel below each item: a small coloured symbol, a caption and a tinted action bar. Reminder status shows a blue alarm, the “Reminder” label and the next upcoming reminder (or the latest past one), including its date when different from the viewed day, plus “· N reminders” when there are several; warning status shows an orange warning symbol and its reason. Reminder actions are Complete, Change time and Remove. Change time opens a focused date/time sheet; Change time and Remove act on the reminder shown and keep any others; removing the last one takes the item out of the filter without deleting it, and reminder edits/removal apply across a repeating series. Warning actions remain Complete, Leave open and Reschedule. A small blue dot marks items with an upcoming reminder; once every reminder has passed, the dot and the filter entry disappear. Completing an item removes it from the reminder filter, its count and its blue row dot, just like resolving a warning. Each occurrence has independent completion/review state and stays on its scheduled day; repeating items do not carry over. The app uses two words for repeating items, everywhere: the **original item** (the master, the first day still in the series) and its **linked items** (every other day). If the original's day is deleted, the next day becomes the original item. Linked items stay linked after one in the middle is deleted. The editor's top line, above the title, says which one an item is:

  - A new pattern: "This item will be unlinked and become a new original item, repeating every Saturday. The original item and other linked items won’t change." In Time view it sits at its reminder or deadline time, with the blue or red dot joined to it, but no track, connector or lane of its own, so the full day's layout doesn't change for it. A reminder that has gone off no longer brings an item in; a deadline does until the item is finished. A day that already shows an item, as itself or as a “Carried to” entry, never shows it as a visitor too. The wash and marker are plain views beside the scale, so the minute tick never redraws the scale; it is given only the passed hour and the covered hour, so it redraws a few times an hour. A day swiped to was built as a neighbour without the tracker, so its rows also report their middles when it gains the tracker, not only when they move (without that, taps there did nothing); and a new day drops the last target, which the page taking over had read as a fresh request and jumped to where the previous day's row had been. Only shown items count, so a filter changes the numbers. The scroll view's bounds already stop at the page's content margins (the bar and the dock), so a row is compared with them plus only the strip from there to the glass (10 points at the top, 26 at the dock); adding the margins again counted rows still in plain view, about a bar's height early. The capsules sit outside the day page, beside the dock, and ask the page to scroll: drawn over the page's scroll view, a tap on one while the page was still moving only stopped the scroll. In today’s full-day List view, small regular-weight tertiary labels mark each nonempty group “Past”, “In progress” and “Upcoming”. List rows and group labels have no horizontal divider lines. The group labels don't show the current time. On today, a small tertiary note says how long an item in progress has left (“1h 10m left”) or how soon an upcoming one starts (“in 25m”), updated each minute; VoiceOver reads it in full. In List view it sits under the scheduled time; in Time view, where the row has room, it sits beside the time after a dot (stacked again at accessibility text sizes). Tapping again immediately restores the item; there are no staged presentation flags or delayed callbacks. - The bottom-centre glass date control shows the full weekday above the date. The calendar is UIKit's `UICalendarView` with multi-date selection kept to exactly one day: a graphical DatePicker and single-date selection both ignore a tap on the selected day, while multi-date selection reports it as a deselection, which is treated as choosing that day again. The viewed day is a black circle and today is a blue number, from the calendar's blue tint (a black circle when today is the viewed day). ## Personas

Personas are the different focuses in a life: **Health**, **Work**, **Family**, **Friends** and **Personal**. Each has its own gradient orb (mint–green, cyan–blue, yellow–orange, pink–red, purple–indigo).

- The glass capsule in the top left shows the current persona with its orb. It starts on **All**, a blend of every persona's colour, which is the normal day view.
- Tap the capsule to open the persona menu, which grows out of it as a Liquid Glass list: All, Health, Work, Family, Friends and Personal, each with its orb and a checkmark on the current one. Choose one to switch to it. VoiceOver reads the capsule as "Persona" with the current choice; the menu is the system one, so it reads naturally too.
- Switching persona cross-fades: the day view and the persona pages fade into each other, so each page's gradient wash blends into the next rather than sliding across. The capsule's label changes at once, and the menu folding back into it is the only motion. On a persona page, swiping left or right anywhere on the page cycles through the personas (left for the next, right for the previous), with the same cross-fade. A swipe that starts on an item never opens or completes it: the persona swipe shares the day pager's gate, which holds off item actions during the drag and for 0.2 seconds after. It wraps from Personal back to Health and never lands on All; going back to All is done from the menu. The swipe only starts for a clearly sideways drag, so vertical scrolling is untouched. VoiceOver users swipe up or down on the capsule for the same cycling (from All, up starts at Health and down at Personal). On All, horizontal swipes still change the day.
- Choosing a persona swaps the day view for that persona's history: every item in that persona (including items that are also in others) grouped by day, newest day first (Tomorrow, Today, Yesterday, then weekday and date), under a small "x/y complete" line like the day view's. The page doesn't repeat the persona's name or orb; instead the top-left button's glass takes on the persona's colour while one is chosen, the same light tint the review and reminder filter buttons show when they're on. The tint switches at once with the label, so it never lingers after going back to All. The day view stays loaded underneath, so going back to All returns to the same day instantly. The review, reminder and deadline filters work on a persona page too: they count the page's items that need review, have an upcoming reminder or an open deadline (an item listed on several days counts once), and narrow the page to them, with the same status panel under each row and "2 to review" (or "with reminders", "with deadlines") in place of the completion count. The page's filter is its own, like search's: choosing another persona starts it at all items, opening Search gives the results a fresh filter and closing it brings the page's back, and resolving the last item in a filter returns to all of them.
- Each day on a persona page lists what that day's list shows of the persona, with the day list's own rows (time ranges, people and locations, progress circles, time left, review and reminder dots) in the same order: untimed and carried items first, then by time. Besides each item's own day, Today is listed whenever today's list shows one of its items, such as a range still running; such an item is counted once. In the history, tap a circle to complete an item or tap the item to edit it. **+** adds an item for today that already has the persona.
- The item editor keeps its explanations out of the way: each section title (Persona, Repeat, Carry over, Reminders, and Schedule for a carried item) has a small (i) that shows or hides that section's explanation, which appears beneath the section's content. They start hidden.
- In the item editor, the **Persona** section shows the five personas, each with its orb. An item can be in several personas, or none: tap a persona to add it (it takes a light tint of its colour, like a reminder pill) and tap it again to remove it. With nothing highlighted, the item has no persona. An item in several personas is listed on each of their pages.
- As in the day list, a carried-over item is shown as itself on the day it is shown (today, or the day it was completed), and every day it was carried on from keeps its quiet "Carried to …" entry in its original place. A repeating item shares its personas across all its occurrences. Its linked items are listed up to three months ahead (generated as the page opens); **Show 3 more months of repeating items** at the top adds three months at a time, keeping your place, and shows only while one goes on further. Non-repeating items planned for later days are always listed. A persona page opens scrolled to today (or the nearest day before it), with what's ahead above.
- The set of personas is fixed for now. Adding, renaming or recolouring them is not built yet.

## Search

A round glass button with a magnifying glass sits just right of the persona button, 8 points from its glass like the field and its ✕, on the day view and persona pages alike. Tap it, or pull the page down past its top, to open **Search**. As the page is pulled, the button drops down into the gap the pull opens and stretches to the right, its icon staying at its leading edge, until the pull is far enough (70 pt): "Search" fades in beside the icon, with a light tap. Pulling further (another 90 pt) goes on morphing it along the same path a tap takes: it widens across the field's row into the field, and its ✕ grows out of its end. Letting go anywhere past 70 pt opens Search, finishing the morph from wherever the pull left it; letting go earlier lets the button spring back up beside the persona button. A fling that bounces at the top never counts, only a held pull, and a pull doesn't open it while the calendar is open or a day swipe is under way. The button follows the persona button as its name changes width.

- The field has a row of its own under the persona and filter buttons, which stay in place and in use while searching. The button and the field are one piece of glass: it moves along one path, down into the field's row while stretching, then across it, so its end passes under the persona button rather than over it. A pull moves it along that path with the finger; a tap, or letting go of a pull, runs the rest of it with one spring (run at the display's full rate like the calendar), so a tap and a pull open exactly the same way. The path is laid out frame by frame from a single animated value (`SearchGlassPath`): animating the start and end shapes, as an earlier version did with two timed springs, cut straight across between them, so a tap looked different from a pull. The label's fade-in comes from the same value as it reaches the row. The icon stays at the glass's leading edge throughout, where the field has it (in the round button that is its middle); an earlier version centred it in the stretched button and slid it aside for the label. The ✕ grows out of its end, and the page fades out behind it, below the top controls. The button's label becomes the field's placeholder. The keyboard comes up once the field has landed: focusing it at the start stalled the morph's first frames.
- **The persona button scopes the search**: choose a persona while searching and only items in it are found, with "No Results in Work" (and a hint to choose All) when nothing in it matches. The persona chosen stays chosen after Search closes, so you land on its page.
- **The filters work on the results**: each is a property of the row, so the review, reminder and deadline buttons count the results that need review, have an upcoming reminder or an open deadline, show only when at least one result qualifies, and narrow the results when tapped, with the same status panel under each row (complete / leave open / reschedule, and so on). On a persona page they narrow the results while searching, and the page again once Search closes. Search's filter is its own: the day's filter stays as it was underneath, and closing Search returns the buttons to the day's counts. Resolving the last result in a filter returns to all results.
- Until something is typed, the screen below the field stays empty, with no explanation, and the keyboard can't be put away: Return, tapping or dragging leave it up; a tap on the empty screen closes Search instead. Once there is text, scrolling the results lowers the keyboard as usual, and the results scroll below the field's row, never over the top controls.
- Closing (the ✕, Escape, or a tap on the empty screen) runs the same path in reverse: the ✕ merges into the field, the field draws in within its row, and then the circle rises back beside the persona button, never crossing it.
- Several details keep it smooth, found frame by frame: the glass stays interactive throughout (switching it rebuilt the glass mid-morph); the icon keeps one colour (animating it to a semantic grey flashed it white); the label and its container aren't laid out until the label shows (even empty, the container took the row's spacing and pushed the icon off centre), and the content isn't clipped, so the label fades in whole rather than being wiped in; typed text and the placeholder fade out at once when closing, rather than with the close's spring, so they never linger.
- ⌘F also opens it, and VoiceOver reads the button as "Search" and the filters as counting results. Under Reduce Motion the button and the field cross-fade instead of morphing.

- An item matches when every word typed appears somewhere in its title, notes, people or locations, ignoring case and accents, so "cafe sam" finds coffee with Sam at Café de Jaren.
- **Dates** in the query are read as dates, and the rest as words (`SearchQuery` in the model). Month names, full or short, in English and the device's language ("november", "nov", "mei"); a month with a day or year, in either order ("november 14", "14th of nov", "nov 14, 2027", "november 2027", "2027 november"); numeric dates in the locale's order ("14/11" in Europe, "11/14" in the US, "2027-11-14", "14-11-27"; an impossible month is read the other way round, so "11/14" works anywhere); a year ("2027"); an ordinal day in any month ("14th"); and relative words: "today", "tomorrow", "yesterday", a weekday (the coming one, today included), "next friday" (after today), "last friday", and "this", "next" or "last" week, month or year. A month without a year finds that month in every year. Dates and words combine: "dentist november" is the dentist in November.
- A date word that is also an ordinary word still finds text: an item matches a date when it falls on it or when its text says the date's words, so "may" finds May and the May fair in October, and "friday drinks" finds the drinks whatever day they're on. Short weekday and month forms that are everyday words ("sun", "sat", "wed", "mar") aren't read as dates.
- An item falls on a date when it's listed on that day: its own day, or a day it was carried on from. Under a date it's listed under the day that matched, preferring its own, so "29 oct" shows that day as the day list does, with its "Carried to today" entries, while "november" lists the same items under Today.
- Results are grouped by the day each item is shown as itself (a carried item under the day it's on now), newest day first with the persona pages' headings (Tomorrow, Today, Yesterday, then weekday and date). The results are the day list's own rows, as on persona pages: tick a circle to complete an item, tap it to open its editor over Search (which stays open behind it, so you can carry on searching), or hold it for Cancel and Delete. An item opened from Search is edited for the day it's listed under.
- A repeating item lists its days up to three months ahead, as on persona pages; **Show 3 more months of repeating items** at the top of the results (the furthest days are at the top) adds three months at a time, generating those days first, and the list stays where it was. The button shows only while a listed repeating item goes on past the last day shown. When the query names a date, every day of a repeating item in that date is listed instead, so "next week" shows the gym all week. Results open scrolled to today (or the nearest day before it), with what's ahead above, and scroll there again as the query, persona or filter changes.
- With nothing typed, tapping or swiping anywhere on the empty screen leaves Search, as the ✕ does. Once there is text, the screen below the results is left alone, so a stray tap doesn't lose the search. **Go to original item** in an editor opened from Search closes Search and goes to the original's day.

## Deleting

- Holding an item for 0.35 seconds puts it in its **focussed state** (`Timo/FocusedItem.swift`), with a medium haptic. It shows history, Cancel (or Uncancel) and Delete; repeating-item deletion choices appear inside the card. Tapping the header opens its editor and returning keeps the card focussed. Cancel/Uncancel updates the item, history and action label in place without closing focus. History entries are separate rows: adding or removing a status line fades it while the buttons and card resize together with the focus animation; sharing and opening deletion choices also keep it open. Tapping outside closes focus; deleting the item removes it. Reminder notifications and Live Activities use the same row anchor. Reduce Motion removes the transition.
  In the day in **List and Time views**, including active filters, focus reveals mounted details inside the original row, using the filter panel's full-size clipped reveal and 0.5-second smooth animation. The original card, title, time and background remain visible throughout; its measured height moves the following rows and sections. Both existing row variants reveal the details, so Anytime reserves the same expanded space in either mode. In Time view, the existing timeline layout places the growing card and any displaced later cards using the same collision rules as filters; its existing track, dot, connector and shared time label remain mounted and follow that layout. No second connector or focus-specific timeline placement is added. There is no copied card, source hiding, offset displacement or source-presentation handover in this path. The page remains undimmed. Under an active filter, its existing status panel remains mounted and visible, and focus details expand beneath it. Completing, cancelling, rescheduling or removing the relevant reminder releases focus if the item no longer belongs in that filter or on that day, including a visiting item whose last relevant reminder is removed. Focus never disables page pan gestures or places a touch-intercepting layer over the interface: scrolling, swiping days, navigation, adding and other item actions remain available. A simultaneous spatial tap observer closes focus on outside taps while letting the same tap reach its control. The opening hold's release cannot open the editor. Holding another visible item uses that row's own press feedback and native long-press recogniser, then switches focus in the same smooth transaction that collapses the previous card. The recogniser cooperates with scroll pans, fails after 10 points of movement and cancels only the Button tap on a successful hold; there is no zero-distance drag competing with a scroll started on a card. Cancel and Uncancel keep the pressed label and history stable during collapse, while the actual item update shares the smooth animation. The action pills share one geometry group, and Cancel/Uncancel uses one stable label, so restoring an item with its completion circle moves all pills together as history shrinks. Changing the displayed day releases that day's focus. A single native scroll animation brings bottom-edge details into view, with no per-frame destination correction; queued requests are cancelled when closing or replacing focus. Closing completion observes the row's own animation and is guarded by the focus token, so an old close cannot dismiss a new focus.
  **Search results** use the same mounted in-place details, outside-tap dismissal and direct focus switching. The existing result stack makes room as the card expands, without a copied card or handover. Query, persona, filter and item changes release focus when that exact result (item and day) disappears; clearing or closing search releases it too. Search focus does not invalidate the day timeline's measurement key. Marker lookup checks each row's current surface gate, so a mounted day or persona row behind search cannot take focus instead of the result. The result grouping, search field animation and existing result-change transition are unchanged.
  **Persona pages** now use the same in-place focus details and direct switching, including under a filter. Focus identifies the exact item-and-day row, since a carried item can appear on several days; another appearance of the same item can take focus independently. Switching persona, opening search, or an item leaving the displayed history/filter releases persona focus. The existing history grouping, page swipe, filter animation and result stack remain unchanged. Every focus entry point uses the original card. The copied-card overlay, dimming, source hiding, handover acknowledgements, closing-position follower and artificial row-displacement code have been removed. No visual or touch-intercepting focus overlay remains.
  The filter's status-panel reveal and `DayTimelineLayout` retain the saved 3 November implementation (`28ca72f`): fixed endpoint proposals, cached measurements and a 0.5-second smooth transition. Only inline focus adds an endpoint measurement key for opening, closing and deletion-choice height changes; it does not invalidate the cache per animation frame. The focus details and row gesture wrapper stay mounted across filter and List/Time switches. Switching gesture branches or inserting/removing the details with the filter replaces row content and interrupts its animation. Sharing, notification routing and track/connector rendering are preserved.

- Every item has the same **Delete**: in its focussed state, and as **Delete item** at the bottom of the editor. A single item is deleted straight away, from the menu and from the editor alike, with no confirmation, since the Undo that follows covers a mistaken tap.
- For a repeating item, Delete shows its choices inside the focussed card, from narrowest to widest as Calendar does: **This linked item only**, **This and following linked items**, and **Original and all linked items**, in red. On the original item they are **Original item only** and **Original and all linked items**.
- Deleting the last item of a section (or of the day) takes the section away in 0.15 seconds, and the “Nothing planned” line fades in just after, instead of the section fading out over the list's half-second animation underneath it. The item editor stays “Your item”, with its Delete row, while it closes after a deletion.
- Every deletion can be undone. A small Liquid Glass capsule appears above the dock, on the day view and persona pages alike, reading Deleted “title” with an **Undo** button, like Mail's Undo Send. It stays 5 seconds (10 with VoiceOver, which also announces it) and fades as glass does. The system's own undo works too: shake, or the three-finger gestures, offer Undo Delete. Undo puts back exactly what the deletion removed: the items with their IDs and completion, the repeating plans as they were (a deleted occurrence's excluded day, an ended series, a removed series), and links to children. Anything changed since then stays as it is. After Undo from the button the system's undo has nothing left to do.
- This linked item only (or Original item only): its day is kept out of the series (its excluded days), so it isn't generated again, also after the original item is edited. The other items keep their completion and cancellation; deleting the original item makes the next day the original.
- This and following linked items: the series ends before that day, and items from that day on are removed; earlier ones stay as they were, with their completion. Older plans that split a series into several parts are handled as one: parts starting on or after that day are removed and the others end before it.
- Original and all linked items: the series and every item in it, past and future, are removed.
- Deleting never deletes other items; a deleted item's linked children are kept and unlinked.

## Scheduling decisions

- One item model with a local day, optional start time, optional end time, completion and an independent carry-over preference. There is no stored task/event type in the new format.
- Calendar.current determines local days, including across daylight-saving transitions.
- An item's scheduled day never changes on its own. An unfinished item with carry-over enabled is shown on today as an untimed item with a "Carried from" line, until it is completed; its scheduled day and time stay as planned. A time range that is still running stays on its own day until it ends.
- Ticking an item off while viewing a past day records it as done on that day (at the current time of day). A carried item completed that way is shown completed on that day and no longer on the days after it, so an event added after the fact can be ticked off on the day it actually happened. Ticked off on today or a future day, it counts as done now.
- Where an item is shown is worked out from its scheduled day, its completion and the current time, so nothing has to run at midnight; the view follows the day as it changes.
- Items with carry-over disabled, completed items and future items are shown on their scheduled day only. Repeating occurrences never carry.
- Every day from a carried item's scheduled day up to the day it is shown on keeps a quiet "Carried to …" entry. On its live day, the item shows a tertiary “Carried from …” line beneath its title, naming its original scheduled date (including the year when different), in List, Time, persona and search rows; VoiceOver reads it too. These entries are not counted towards completion or reminded about again; ticking one off completes the item on that day. Each entry stays in the item's original place rather than in a block below: on its scheduled day a timed item keeps its time among the Scheduled items (and on the timeline in Time view), otherwise it sits among the Anytime items. It uses the normal row and card (same fill as every other item), with a › circle, the normal title colour while unfinished and the "Carried to …" line. While the item is unfinished the entry keeps its small orange dot, so an earlier day still shows what was left open there, and the entry is counted in that day's orange review filter, whose panel says “Unfinished, carried to …”; Leave open takes it out of that filter but keeps the dot. It has no blue reminder dot. A filter keeps an entry when the entry has that filter's dot (orange review, red deadline) and hides it otherwise.
- Rescheduling an item moves its trail with it: planned for a later day, the earlier days let it go. Plans saved before this (when carrying moved an item's day to today) are restored to their scheduled day once on opening, with time ranges shifted back; a single time that was dropped when it moved cannot be recovered.
- Past days otherwise contain the items still scheduled there, not a snapshot of the original plan. No historical copies are generated.
- Time ranges appear on every day they overlap; ending at midnight excludes the following day.
- Changing a start time or day preserves an existing duration. Removing the start time also removes the end time.
- Stored parent relationships are preserved, but linking controls and parent completion suggestions are temporarily disabled in the interface.
- Time-passed suggestions never change completion state. Leave open dismisses the suggestion until the schedule changes or completion is undone: the item leaves the review filter and its count, but keeps its orange dot while it is unfinished (VoiceOver reads “Left open”). A carried item is not flagged for its old time.
- Cancelling is a state of its own, separate from completion (`cancelledAt` beside `completedAt`), and the two never stand together: cancelling clears completion, and uncancelling leaves the item open. A cancelled item doesn't carry on: like a completed one, it stays on the day it was cancelled from (a past day when cancelled while viewing it, otherwise today), with the usual "Carried to" entries on the days before. It never needs review, shows no time progress or "in 25m" note, and isn't in the reminder filter; its reminders are kept but don't notify, and come back if it is uncancelled. The "x/y complete" counts leave cancelled items out of the total. Rescheduling or editing a cancelled item keeps it cancelled.
- Cancelling a repeating item cancels only that occurrence, like completion; editing the series keeps each occurrence's cancellation, and new occurrences start uncancelled.
- Parent selection enforces one level of linked children and rejects missing parents and cycles.
- The screen follows today across midnight when viewing today; intentionally viewing another day does not jump back.

## Persistence

The plan is stored as an atomically written, versioned JSON document, Timo/plan.json. With the App Group `group.com.timovijn.timo` it lives in the group's shared container, so the lock screen widget can read it; a plan saved earlier in the app's own Application Support moves there once, at launch. Without the App Group it stays in Application Support/Timo/plan.json (`Timo/PlanLocation.swift`). On the simulator every device instead shares one file on the Mac, ~/Library/Application Support/Timo Simulators/plan.json (`PlanLocation.simulators`), so an iPad simulator shows what was planned on the iPhone one until iCloud sync carries plans between real devices. The first simulator to open finds it missing and copies its own plan in (copied, not moved, so each device's own file stays to go back to). Several simulators can be open at once, so each watches the file's folder and takes up another one's save straight away (`PlanStore.reloadFromOtherDevice`); otherwise an open iPad would write its older plan back over the iPhone's next change. Each store remembers the bytes it last read or wrote, so its own saves don't reload it. The shared location also resolves from the simulator data directory if the host-home launch variable is missing. The folder is created before watching, and foreground/day refreshes reload the shared file before reconciling, so suspended simulators catch up. Rebuilds update the installed app and retain this plan; they must not uninstall it or seed replacement sample data. The plan is small and local; this keeps version one dependency-free and allows scheduling tests to run without an iOS runtime. SwiftData is not used in this implementation. A later storage migration can retain the existing item IDs.

The version 7 format stores each item's personas as a list (also on repeat templates), in a fixed order. It reads existing version 1–6 plans without changing item IDs or schedules: version 6 kept a single persona, which opens as that one; older plans open with none. Personas this version doesn't know are left out. Repeat templates were added in version 5. A cancelled item stores `cancelledAt`; the key is only written for cancelled items and older plans open with nothing cancelled, so it didn't need a new version.

### iCloud

**Sync with iCloud** in Settings keeps the plan in the person's private iCloud database (CloudKit, `CKSyncEngine` in `Timo/CloudSync.swift`), as a backup and so it's the same on each of their devices. It's off until turned on. There is nothing to sign in to in the app: it uses the iCloud account the iPhone or iPad is signed in to, and without one the section says so with a button to the Settings app; signing in there takes effect when the app returns to the foreground. The section shows Checking, Syncing, "Up to date · synced 2 minutes ago", or what went wrong in orange. Signing out of iCloud, switching accounts, or deleting the app's data from iCloud turns sync off and says why; the plan always stays on the device, and turning sync off leaves the iCloud copy as it was.

The JSON file stays the local copy. Each item and repeating plan is one record in a "Plan" zone, holding the value as the same JSON (record types `Item` and `Series`, field `payload`), so records follow the app's own format and migrations rather than a CloudKit schema of their own. Every save queues what it changed (`PlanStore.commit` compares before and after); changes fetched from iCloud are written back through `PlanStore.applyFromCloud`, which doesn't queue them again. A save is sent 0.3 seconds later (`CloudSync.sendSoon`), which gathers the saves of one action into one send; left to itself the engine picks its own moment, which took many seconds, and its schedule stays as the fallback with its retries. Other devices hear of it by push, and returning to the app fetches too, in case a push was held back. Turning sync on for the first time uploads the whole plan; a second device's own items are kept alongside. The engine's state and, per record, its system fields and the value iCloud last had live in Application Support/Timo/sync.json, removed when sync is turned off. The app has the iCloud (CloudKit, container `iCloud.com.timovijn.timo`) and push entitlements (`Timo/Timo.entitlements`) and the remote-notification background mode, so other devices' changes arrive without opening the app. Only a paid Apple Developer Program team can sign those, so the `TIMO_ICLOUD` build setting decides whether a build has them; it's YES for the app and the widget, on devices and the Simulator, in both configurations. With NO, as a free team would need, the build has no entitlements and Settings shows no iCloud section (creating a CloudKit container without the entitlement would crash).

When two devices change one item, the edits are combined field by field (`PlanItem.merged(base:mine:theirs:)`) from the version both started from: whatever this device changed wins, everything else comes from iCloud. The schedule (day, start, end), completion with cancelling, and the repeat pattern are each taken as one, so a merge never pairs one edit's start with another's end. A change still waiting to be sent is merged with a fetched one and sent after it. Repeating plans and deletions aren't merged: the latest wins, and an item deleted on one device is deleted everywhere.

A repeating item's occurrences get their ID from the series and the day (`PlanItem.occurrenceID`), so two devices generating the same days produce the same records rather than doubles. When an occurrence shifted or detached by an edit already holds the derived ID, a new one falls back to a random ID. Occurrences saved before this kept random IDs, so after a sync one day can arrive twice; `Planner.mergeDuplicateOccurrences` folds them into one, choosing from the IDs alone so every device keeps the same copy, passing on a completion and moving children over.

Every item opens Timo’s own Sharing screen immediately from the editor or focus view. It shows remembered participants and offers direct sharing with connected people, with progress and errors inside the screen. Invite someone new opens Apple’s sharing flow to send the first invitation link; Manage sharing opens its participant/access controls. The system screen retains the custom people thumbnail. Existing items have a **Share item** row at the bottom of the editor, below Notes and above Cancel/Uncancel and Delete, instead of an add pill. Cancel/Uncancel edits the draft and takes effect on Save. The focussed view offers compact Share, Cancel/Uncancel and Delete pills in one row, aligned with the history text’s left edge, with the same intrinsic pill sizes in List and Time views and centered icons and labels inside each pill and a balanced people icon for Share; they stack when the available width or text size needs it. Single items can be shared with other iCloud users from the **Sharing** section of an existing item's editor (`Timo/CloudSharing.swift`), which needs iCloud on and opens the system's sharing sheet (presented from UIKit, since inside a SwiftUI sheet it comes up blank). Each shared item has a zone of its own, `Share-<id>`, shared as a whole with a zone-wide `CKShare`; a repeating item moves with its whole series, and days generated later join it. The move saves the records to the new zone and then queues the old ones' deletion, and because either can reach another device first, only the zone a record is in now can delete it. A share is private and read-write by default, and a share nobody joined doesn't count as shared, so opening the sheet and leaving changes nothing visible. The sharer's zone is in their private database; everyone else reaches it through the shared database with a second `CKSyncEngine`, so each record's zone (kept in sync.json) decides which engine sends it. One person ticking a shared item off completes it for everyone, and everyone can edit it or delete it for all. `PersonalDetails` (reminders, personas, a dismissed review) stays each person's own: shared records leave it out (`PlanItem.forSharing`), and it syncs between a person's own devices as an `Overlay` record in their "Plan" zone. A shared item says "Shared" on its row's small line. A link needs the app, opens it through `TimoSceneDelegate`, and turns iCloud on if it was off, since a shared item can't arrive without it. If the sharer stops sharing, their item stays in its zone, unshared, and it's gone from everyone else's plan; someone who leaves loses their copy only. Someone who has joined a share is remembered (`CloudSync.people`); the direct-sharing support remains in CloudSync, but the editor and focus actions both open Timo’s Sharing screen, where remembered people can be added directly. CloudKit can't deliver a share by itself, so the app writes an `Invitation` record, holding the new share's URL and the recipient's user record, into a zone both people are already in, and the recipient's app accepts it, removes the record and posts a notification naming the sharer. Accepting needs no answer, since it comes from someone already shared with, and an invitation stays in sync.json until accepting works, as a fetch delivers it only once. An invitation lives in a private shared zone rather than the public database, so nothing about it is public and no index is needed; the cost is that the first share with a new person still goes by link, through the system sharing screen. If every zone with someone has ended they drop off the remembered people list. Not done: a link doesn't jump to the item's day, and a linked child item isn't shared along with its parent.

iCloud doesn't tell an app which devices use it, so each device keeps a `Device` record of itself in the "Plan" zone (`CloudSync.devices`), and Settings lists them under **Devices**, this one first. A device checks in when sync starts and when the app returns, at most hourly, so "seen" can be up to an hour behind and doesn't show a device that has sync on but hasn't been opened. Its record goes when sync is turned off there, and one not seen for 60 days leaves the list. Devices are named by model (iPhone, iPad), since a device's own name needs an entitlement Apple grants by request.

Messages name the device ("this iPad" or "this iPhone"); the sync itself doesn't depend on it, so an iPad on the same account is just another device. Sync between two signed-in devices has been checked on a real iPhone and iPad; sharing still has to be checked with a second Apple Account. Before a TestFlight or App Store build, the CloudKit schema (created by the first development sync) has to be deployed to production in the CloudKit Console.

Writes complete before in-memory state is published. Save failures are surfaced. An unreadable or unsupported existing document is left untouched and saving is disabled. Deleting the app deletes its local plan. There is no backup/export UI yet.

## Reminders

Local notifications are scheduled after a successful save and refreshed at launch or foreground entry. Completion, cancelling, deletion, disabling a reminder and time edits update pending notifications; notifications also present while the app is open. Tapping a reminder opens its item in the focussed view, centred on today when it appears there, otherwise on its scheduled or carried day. This also works when the notification launches the app; reminders for deleted items are ignored. Notification delivery must still be checked on the iPhone, including permissions and Focus settings.

The nearest 64 future reminders are scheduled, replenished on subsequent saves or app entry. Reminders that have passed are never repeated for a carried item. Each reminder is its own notification, delivered as Time Sensitive: it's something asked for at that moment, so it can break through a Focus where the user allows timo's Time Sensitive notifications (iOS asks per app and per Focus). The entitlement follows the iCloud switch, so for now it's only on in the Simulator; elsewhere reminders arrive as ordinary notifications. Changing an existing start shifts all its reminders by the same amount; changing an untimed item's day shifts them by calendar days. Removing an item's start preserves its explicitly set reminders.

Startup does not create or focus an off-screen keyboard field. The previous `KeyboardWarmup` intentionally moved first-keyboard initialization onto the main thread 300 ms after launch; Xcode device logs showed hundreds of keyboard-factory warnings from that path. It has been removed so launch does not pay that artificial keyboard cost. The first actual text-field interaction now initializes the keyboard normally. Cloud sync also skips sends when an engine has no pending database or record changes, and returns no record batch for an empty scoped request rather than constructing an empty batch. A fresh Xcode run on the connected iPad after these changes showed zero keyboard-factory, geometry-cycle and empty-resource-batch messages. Two system `cannot add handler to 0 from 0 - dropping` messages remained; the system console was not completely silent.

## Guide my day

**Guide my day** (Settings, off by default) follows today's timed items with Live Activities on the Lock Screen and in the Dynamic Island. Each time range gets its own activity from its start: its title and persona colour, the minutes left ("46 minutes left", whole minutes because the dimmed Lock Screen hides seconds), a bar filling as the time passes, its range, "Next" with the following timed item of today, and a **Complete** button. The compact Dynamic Island shows the persona dot and a ring filling over the range. The countdown, bar and ring run by themselves. At the end the activity goes stale and reads "Time's up", keeping the Complete button until the item is ticked off. Completing it, from the button or in the app, ends the activity. In the expanded Dynamic Island the corners hold the persona dot and time ring, as in the compact island, the title sits between them below the camera, and the time left shares a line with the range under the bar. In a corner, "48 minutes left" wrapped into fragments and ran into the title. The time left is a live count, which takes all the width it's offered, so it fills the rest of a line; `fixedSize` on it stopped the whole activity drawing, compact view included. iOS always opens the app when an activity is tapped and only a long press expands the island, so a tap (`timo://item/<id>`, `GuideAttributes.itemURL`) goes to the item instead: today's page, with the card scrolled to the middle and in its focussed state, where tapping the card opens it. It waits only for what's in the way, an editor closing or the page changing, so on today's page the card takes focus as soon as the link arrives, and about a quarter of a second later from another day. It goes through the row's own marker, so the card is laid out as for a hold, with the time beneath the title in Time view. Buttons in the expanded island work without opening the app. After a reinstall a running activity can stay blank in the Simulator until it's rebooted.

Which items it follows comes from `DayGuide.stops` in the model: unfinished time ranges that start today (or began yesterday and are still running). Anytime items, single moments, carried items and ranges of several days are left out; their reminders cover them. Overlapping ranges each get their own activity, and the earlier one shows the later one as Next.

The app keeps the activities in step after every save and whenever it comes to the foreground (`DayGuideActivities`): items that are running get an activity right away, and the next four to come are scheduled to start at their start time (iOS 26), so they appear without opening the app. A scheduled activity announces its item when it starts; a reminder set at exactly that moment isn't also delivered. An activity is ended when its item is completed, cancelled, moved or deleted, or when the setting is turned off. An item whose time ended keeps its activity, but none is started for it afterwards. Without push updates (which need the paid developer account), "Next" is as the app last saved it, and items further ahead are only scheduled when the app next opens. How many scheduled activities iOS accepts and how reliably they start still need checking on a device.

## Lock screen widget

The **Today** widget (`TimoWidget/`) shows how many of today's items are done, the same count as the day view's "x/y complete" (`DayProgress` in the model): cancelled items aren't counted, and carried items count on the day they're shown. It comes in two lock screen sizes: a ring with "3/5" in the middle, filling as items are done (a checkmark when nothing is planned), and a line above the clock, "3 of 5 done" ("Nothing planned" on an empty day). VoiceOver reads "3 of 5 done today".

It reads the plan from the App Group's shared container. Every save reloads it; otherwise its timeline changes when a running range ends and at midnight. Like iCloud, the App Group follows `TIMO_ICLOUD`, since a free team may not support it; without it the widget shows "Open timo".

## Verification and remaining work

- The latest iPhone application target builds successfully through Xcode with zero errors or warnings. Direct command-line builds in this session remain blocked by the SwiftUI macro host sandbox restriction. Core scheduling tests and isolated UI type-checks run separately.
- The core XCTest suite covers migration, independent carry-over, carried-over entries on earlier days, duration editing, overnight scheduling, recurrence (patterns, DST, completion, persistence, distant dates, series edits and deletion) and personas (persistence, older and unknown values, history grouping, carried and repeating items) and cancelling (carry-over, review, reminders, per-occurrence repeats and persistence) and sync groundwork (occurrence IDs shared across devices, folding doubled occurrences, personal details, field-by-field merging).
- Simulator launch and interactive visual verification were blocked by this automation session's connection to CoreSimulator. On-device testing, VoiceOver, maximum Dynamic Type, dark mode and reduced motion/transparency still need hands-on verification. Successful compilation does not establish visual quality.
- The interface uses native navigation/toolbar materials and a Liquid Glass add button. System accessibility preferences control the native materials; custom completion animation respects Reduce Motion.
- Untimed tasks currently follow creation order. Drag reordering is not implemented.
- No custom icon yet; the app uses the development placeholder.
- iCloud sync is checked on real devices; sharing is built but not yet checked between two Apple Accounts (see iCloud under Persistence). Projects and AI remain out of scope. Nothing has been pushed to GitHub or deployed to Vercel.

The date dock keeps its lower screen position. Its weekday and date stay visible; the brief relative date (Today, Tomorrow, Next, Last, etc.) appears in a small glass pill above it for 1.5 seconds. In Time view, the later-items pill sits above the relative-date pill while it is visible and settles back towards the dock when it fades. The spacing uses the relative pill’s measured height, including larger text sizes. All three pills use the same 0.25-second ease-in-out fade and four-point entrance/exit movement (without travel under Reduce Motion), and label changes cross-fade. A disappearing count pill keeps its last positive count while fading, so zero earlier/later never flashes. The earlier pill moves down to appear and up to disappear, mirroring the later pill’s upward entrance and downward exit. Both bottom pills share one local animation: the relative pill stays built and fades while the later pill moves by a rendering offset, without animating list layout. Its timer updates only the overlays, rather than the day view or pager. Day settling also requests the display’s full animation refresh rate.

Timeline overflow counts and row positions are reported together so an immediate tap after a count change has a valid target. Each tap gets a distinct scroll anchor; the scroll runs only after that anchor reports its layout, and superseded requests are ignored.

Debug builds leave copied widget binaries unstripped (`COPY_PHASE_STRIP = NO`), avoiding attempts to strip already-signed preview dylibs when embedding the extension. Release stripping keeps its standard settings. Cloud sync’s immutable zone and device IDs are nonisolated so its Codable helper types can read them safely.

In List view, filtering relies on rows collapsing to bring the first match upward; it does not call `ScrollViewProxy.scrollTo` during the same update. Time view uses the original single native `scrollTo` approach in the filter animation’s transaction: opening a filter targets its first matching Time-view row at the top, and closing it targets the stable page-top header. There is no custom scroll timer, per-frame row following, settling heuristic or delayed scroll task. Filtered Time view reserves one viewport of bottom scroll room so late items can reach the top. Timeline visibility measurements update their non-observed coordinate cache directly, without SwiftUI row-state writes on every moving frame.


Item cards retain their existing opaque system-background fill throughout mode and layout animations. List/Time switches select the visible row variant immediately and animate its placement instead of crossfading card opacity. There is no additional per-item backing view or backing-layout bookkeeping.

Scroll-phase callbacks keep gesture bookkeeping in a non-observed reference and defer search opening/resetting and editor-popover dismissal to the next update. They avoid redundant UI state writes and do not change layout synchronously inside the phase callback, addressing the runtime “OnScrollPhaseChange Modifier tried to update multiple times per frame” warning.
